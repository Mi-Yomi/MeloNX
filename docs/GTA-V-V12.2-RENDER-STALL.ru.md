# MeloNX v12.2: остановка кадров и результаты GPU-запросов

Экспериментальная сборка на основе v12.1 (`9a7d1e83d33c`). В исследованном
прогоне кадры перестали поступать после 9105 показанных кадров, хотя звук,
цикл GPU producer и интерфейс продолжали работать. В логе нет OOM, ошибки
Vulkan или отказа host import; минимальный измеренный запас памяти около
690 MiB. Эти данные не позволяют свести зависание к размеру текстур и не
содержат точного стека заблокированного гостевого потока.

## Исправления

- **Пробуждение ожидающих GPU-ресурс.** `BufferMap` и `SyncMap` больше не
  используют один AutoResetEvent для разных ID. Публикация готового ID
  пробуждает всех ожидающих, каждый проверяет свой ID под тем же lock.
  Освобождение SyncMap прекращает ожидание с явным исключением.
- **Кэш GPU-счётчиков.** Находится и ожидается первый элемент кэша; unmap
  правильно удаляет события при границе между ключами и после последнего
  ключа. Отложенный callback удалённого события не пишет в новую привязку.
  Нулевые и переполняющиеся диапазоны обрабатываются без wraparound.
- **Отправка query results.** Завершённый запрос копируется и тогда, когда
  render pass уже закрыт. Копирование записывается перед reset/submit.
  При простое backend обслуживает pending работу после 8 мс без команд,
  включая случай, когда producer сам ждёт результата. Отправки пустых
  command buffers нет; внутри незавершённой GAL-команды flush не выполняется.
- **Ожидание и порядок результатов.** Неполный результат и sentinel не
  выдаются игре при таймауте. Consumer сохраняет событие и повторяет ожидание;
  при остановке оно отменяется. Накопленный счётчик изменяет один consumer,
  а reset и возврат query в пул используют один lock.
- **Условное рисование.** Vulkan-путь с отключёнными native conditional
  rendering calls должен использовать фактический результат счётчика на CPU.
  Threaded-обёртка получает реальный ответ backend вместо предположения, что
  условие уже будет выполнено на GPU. Цена корректности — синхронизация при
  таких условных решениях.
- **Временные страницы.** Пул удерживает несколько массивов до 4 KiB вместо
  повторного выделения почти всей пачки. Общие ограничения остаются прежними:
  64 MiB и 64 возвращённых массива; leased данные не освобождаются. Это
  уменьшает churn, но не устраняет все расходы эмуляции. Малые страницы не
  вытесняют большие буферы конвертации из заполненного пула.
- **Диагностика зависания.** При остановке кадров лог содержит активную
  GAL-команду, прогресс очереди, pending/retired/timeouts query и до 64
  снимков managed metadata гостевых потоков. Нет чтения TLS/памяти игры,
  принудительной приостановки или ожидания kernel lock. Повторное сообщение
  UIKit о той же частоте экрана больше не сбрасывает pacing и не засоряет лог.

Порядок записи query сверяется с
[требованиями Vulkan](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdCopyQueryPoolResults.html):
копирование результата выполняется вне render pass. Native MoltenVK сохранён
на закреплённых исходниках v12.1 с обоими backport, включая исправление host
import. CI пересобирает его и повторяет обязательное GPU-копирование на macOS;
переписывать драйвер без выявленного native дефекта в этом изменении не требуется.

## Проверки и ограничения

Новые тесты используют реальные ожидающие потоки, настоящий query consumer,
CommandBufferPool и перехват Vulkan-вызовов для проверки порядка. Обязательный
набор v12.1 сохранён и расширен; CI публикует фактические TRX, проверку полноты,
native-отчёт, исходники, SHA-256 и dSYM.

Исправлены воспроизводимые дефекты кода. Их наличие не доказывает, что каждый
из них вызвал именно исследованную остановку кадров. Прохождение GTA V на
iPhone этой сборкой ещё не подтверждено. Диагностика гостевых потоков отражает
изменяемые поля, а не атомарный снимок ядра; она работает при живом PresentLoop,
как в исследованной сессии.

## Установка и проверка на iPhone

Подписать IPA, сохранить прежние разрешения памяти и включить JIT. Для первого
сравнения оставить те же настройки и сохранение: 4 GiB гостевой памяти,
прежний режим HostMappedUnsafe, backend Auto/On, Switch VSync и исходный масштаб.
Снижение масштаба отдельно можно оценивать после проверки прежнего места
зависания; одновременная смена нескольких настроек затруднит сравнение.

Проверить снежную сцену после аварии фургона, переход к психологу и начало
управления Франклином. Если кадры снова остановятся, дать игре около 20 секунд,
затем остановить её и экспортировать новый core log, memory.jsonl и session.json:
в логе появятся `GPU frame stall` и `Guest stall threads v1`.
