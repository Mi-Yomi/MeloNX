# MeloNX v12: исправления рендера и времени жизни ресурсов

Продолжение ветки v11 (`39df48fe6a35f39226093bfcdcad5d337cdd2f7d`).
Цель — уменьшить лишние выделения и удержание памяти во время переходов GTA V
между сценами на iPhone 16 Pro Max. Прохождение сцены у психолога и начала игры
за Франклина на этой сборке пока не подтверждено устройством.

## Что изменено

1. **GPU-буфер расширяется от своего конца.** Раньше эвристика повторно
   учитывала префикс существующего буфера и могла поглотить соседние ресурсы.
   В регрессионном примере небольшой запрос в конце 64-КиБ буфера создавал
   156 КиБ вместо 96 КиБ. Проверяются размер, сохранение соседнего handle и
   содержимое объединённых участков. Лимиты кэшей для этого не снижались.
2. **Буферные текстуры сохраняют неизменившийся Vulkan view.** Создание любого
   постороннего буфера раньше инвалидировало view через общий счётчик.
   Теперь сравниваются диапазон и уникальная идентичность его backing storage.
   Повторное использование числовых GAL/Vulkan handles корректно инвалидирует
   view; уже отправленные GPU-команды сохраняют свою ссылку до завершения.
3. **Отложенные CPU-записи хранятся разреженно.** Вместо `new byte[Size]` на весь
   GPU-буфер арендуются только затронутые страницы по 4 КиБ. При построении
   staging mirror неизменённые байты берутся из native mapping, изменённые —
   из этих страниц. Загрузки объединяются в ограниченные блоки до 64 КиБ.
   Проверяются пересечения, частичное удаление, ошибки выделения/загрузки и
   повторный вход при завершении render pass. Это меняет CPU-копии буферов,
   а не разрешение или формат игровых текстур.
4. **Уничтоженные ресурсы перестают удерживать managed-владельцев.** `Auto<T>`
   очищает ссылки на backing, зеркала, waitables и дочерние ресурсы только после
   последнего resource reference. Запрос `Dispose` не освобождает память,
   которую ещё используют command buffers. Страницы pending mirror возвращаются
   в ограниченный пул на том же рубеже уничтожения native-буфера.
5. **MoltenVK пересобирается из исходников.** Закреплены MoltenVK 1.4.0 и семь
   зависимостей. Перенесён autorelease-pool fix из upstream
   [5ff9bced](https://github.com/KhronosGroup/MoltenVK/commit/5ff9bcedada97c69686102e00f427355d1096b30)
   для временных Metal-объектов при создании buffer view. Сборка сохраняет
   реализацию descriptor tracking версии 1.4.0. Артефакт включает исходники,
   патч, лицензии, хеши, ABI-проверку и соответствующий dSYM.
6. **Учёт использования охватывает весь буфер.** `VK_WHOLE_SIZE` при переходе
   в signed API становится `-1`. Раньше bitmap мог отметить только первую
   страницу; теперь специальный размер нормализуется в остаток буфера и в
   проверках чтения/записи, и при выгрузке pending data. Слишком большой
   диапазон ограничивается без переполнения целого числа.
7. **Редкий путь загрузки сохраняет корректность GPU-команд.** Когда быстрая
   запись и staging отказывают, временная копия завершает render pass перед
   `vkCmdCopyBuffer`. Освобождение временных и производных буферов не должно
   подменять command buffer посреди серии pending-записей; учёт отложенного
   освобождения сохраняется до следующей безопасной отправки команд.

## На чём основаны изменения

В предоставленном прогоне v11 footprint достиг 6120,5 МиБ, оставалось около
23,5 МиБ доступной процессу памяти. Это согласуется с сильным давлением памяти;
без соответствующего системного `.ips` окончательная причина завершения
процесса не установлена.

Массовое создание буферов (около 2600–2700 в секунду) происходило ещё при полном
кэше 128 МиБ. В этот эпизод доминировала обработка команд эмулятором. Позднее FPS
восстановился примерно до 30, но footprint вырос ещё на 571 МиБ за 38 секунд.
Эти два эпизода нельзя считать одной доказанной причиной.

Исправлен и анализатор логов: он восстанавливает разбитые NSLog строки census.
В этом прогоне все зарегистрированные преобразования были `Native`, без ошибок.
Это не даёт оснований объявлять декомпрессию текстур причиной многогигабайтного
роста. Логический размер texture storage, allocator memory и driver allocation
описывают пересекающиеся уровни учёта; их нельзя складывать как независимую RAM.
Исходные пользовательские логи и детальный отчёт в публичный репозиторий не входят.

## Сборка и проверка на устройстве

GitHub Actions собирает точный commit с Xcode 26.2 и .NET 10.0.400. Публикация
разрешена после C#, memory, Swift, Python и native ABI/package gates. Результаты
и точное число выполненных тестов добавляются ниже автоматически. Тесты на runner
не заменяют проверку Apple GPU и реального лимита памяти приложения.

IPA требует переподписи и JIT. Для первого сопоставимого прогона сохраняйте
одинаковые game build, save point, настройки и состояние shader cache. Можно
начать с handheld, 0.5x, AA off, существующего профиля 4 ГиБ guest RAM и JIT Auto;
изменение guest RAM одновременно со сборкой усложнит сравнение. Get More RAM
нужно активировать так же, как в предыдущем успешном запуске. Удалять сохранения
или всю папку приложения не требуется.

Нужен прогон через обе проблемные сцены и несколько минут управления после них.
Если приложение завершится, сохраняйте `.ips`, `memory.jsonl`, `session.json`
и core log от одного запуска вместе с номером сборки. Для символикации используйте
только приложенный к этой IPA архив symbols с совпадающими UUID.
