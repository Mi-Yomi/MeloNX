## Результат и границы проверки

Применена идея ограничения частоты и одновременности сохранения Vulkan-кэша,
независимо реализованная в C# в архитектуре MeloNX. Дополнительно исправлены
применение Expand RAM, доступ к NRO, время жизни текстур, освобождение JIT/Vulkan-памяти
при ошибках, небезопасное чтение настройки первого запуска и Vulkan feature flag.
Обновлена зависимость desktop-приложения с известной уязвимостью.

Это статический инженерный аудит запуска, iOS build pipeline, JIT, диагностики памяти,
кэширования Vulkan и соответствующих подсистем Eden с компиляцией и целевыми тестами.
Он не является построчной проверкой всех тысяч файлов, всех служб HLE, всей математики
шейдеров и всех сторонних бинарных библиотек. Замеры на iPhone, исполнение Darwin JIT API
и запуск конкретной сборки GTA V в этой среде не выполнялись.

## Внесённые изменения

### 1. Ограничение сохранения Vulkan-кэша

Раньше `PipelineCacheManager` сериализовал кэш каждые 64 события worker без интервала
по времени. Сериализация выделяет массив вплоть до 128 MiB. При уменьшении размера
возвращённых данных `Array.Resize` мог дополнительно скопировать весь нужный диапазон.

Теперь первое сохранение выполняется после 64 событий, повторные попытки — не чаще
раза в 30 секунд на worker по монотонным часам. Общий неблокирующий gate разрешает
одну периодическую сериализацию одновременно. Отказ из-за времени или занятого gate
сохраняет накопленные события; следующая проверка происходит при следующем событии.
Неудачная попытка тоже сохраняет pending и получает задержку перед повтором.

`GetPipelineCacheData` остаётся на владеющем worker между операциями создания pipelines.
Финальное
объединение и сохранение после остановки workers обходят этот интервал. На диск пишется
ровно возвращённый диапазон данных без дополнительного массива `Array.Resize`.

Файлы: `PipelineCacheManager.cs`, `PipelineCacheCheckpointPolicy.cs`, тесты
`PipelineCacheCheckpointTests.cs`. Идея pacing взята из Eden #4294; код реализован
самостоятельно в C#, C++ из Eden не копировался. `Eden/LICENSE.txt` содержит GPLv3,
а `MeloNX/LICENSE.txt` — MIT; README MeloNX при этом упоминает GPLv3, что является
существующим расхождением документации.

Компромисс: при аварийном завершении могут потеряться изменения кэша после последнего
checkpoint; это может вызвать повторную компиляцию при следующем запуске. Планировщик
имеет максимум два workers; при `Environment.ProcessorCount == 6` получается один.
Поэтому выигрыш от запрета двух одновременных сериализаций зависит от устройства,
а снижение частоты выделений/записей полезно и при одном worker. Рост FPS и уменьшение
JetSam на GTA V пока не измерены.

Отдельно убран `ExternallySynchronizedBitExt`: наличие extension проверялось,
но feature `pipelineCreationCacheControl` при создании устройства не включался.
Это нарушало VUID 02892. Используется стандартная внутренняя синхронизация Vulkan,
а неиспользуемое имя extension удалено из запрашиваемых расширений.
[Спецификация Vulkan](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheCreateInfo.html).
Лимит 128 MiB относится к сериализуемому файлу и временному массиву, а не ко всей
нативной памяти pipeline cache. При загрузке shader cache есть отдельные восемь
translation threads; ограничение scheduler до 1–2 workers не ограничивает их.

### 2. Освобождение частично созданного JIT mapping

Раньше ошибка `vm_remap` оставляла RX mapping, а ошибка `vm_protect` — RX и RW mappings:
поля владения присваивались только после успешного окончания всей процедуры.
Теперь владение фиксируется сразу после каждого успешного выделения; последующая
ошибка освобождает уже созданные mappings. Повторный `Dispose` безопасен, освобождение
второго mapping выполняется и при исключении первого cleanup.

Файл: `src/Ryujinx.Memory/DualMappedJitAllocator.cs`. Восемь тестов с подменёнными
нативными операциями проверяют ошибки выделения/remap/protect, нулевые адреса,
повторное освобождение и исключение cleanup. Реальные TXM mappings на iPhone этим
не проверяются. Выбор TXM и fallback BreakpointJIT сохранены.

### 3. Чтение версии при первом запуске

`lastAppversion` по умолчанию содержит пустой `Data`, но `MeloNXApp.swift` безусловно
читал из него `Float`. В исходниках регистрации непустого default не найдено.
Добавлены проверка точного размера данных, `loadUnaligned` и обработка нечислового
значения. Пустая/повреждённая запись больше не передаётся в небезопасное чтение.
Формат существующих сохранённых настроек сохранён. Проверка Swift/Xcode и первого
запуска новой сборки на устройстве описана ниже. `loadUnaligned` присутствует в выбранном
Swift и не требует повышения deployment target iOS 15.
[Исходник Swift](https://github.com/swiftlang/swift/blob/swift-6.2.3-RELEASE/stdlib/public/core/UnsafeRawBufferPointer.swift.gyb#L443).

### 4. Зависимость desktop-приложения

При чистом restore обнаружено предупреждение NU1903 для транзитивного
`Tmds.DBus.Protocol 0.21.2`. Добавлена прямая фиксация совместимой исправленной
ветки `0.21.3` только в desktop-проекте Ryujinx. Advisory описывает атаки от другого
участника той же D-Bus шины; это не установленная причина вылета GTA V на iPhone.
[Официальное уведомление и исправленные версии](https://github.com/advisories/GHSA-xrw6-gwf8-vvr9).

### 5. Настройка Expand RAM и доступ к NRO

Swift передавал `ExpandRAM` через ABI, но `Library.cs` всегда создавал конфигурацию
4 GiB. Теперь выключенная настройка выбирает прежние 4 GiB, включённая — 8 GiB,
как уже обещает интерфейс. Выбор записывается в лог. В kernel application pool
это соответственно 3285 и 6964 MiB. ABI и значение по умолчанию не изменены.
Это размер гостевой памяти, а не разрешённая iOS память процесса и не размер JIT-кэша.
Ранее сохранённое `true` теперь действительно увеличивает память и может повысить
давление на память iPhone. Для первого сравнения на iPhone 16 Pro Max использовать
выключенный Expand RAM; 8 GiB не объявляется рекомендуемым режимом GTA V.

`ProcessLoader.LoadNxo` открывал NRO через `FileStream(path, FileMode.Open)`, запрашивая
чтение и запись. Теперь явно запрашивает только чтение с `FileShare.Read`.
Читаемый NRO с запретом записи больше не требует излишних прав. Время жизни потока,
необходимое для встроенного RomFS, сохранено.

### 6. Время жизни текстур

В `AutoDeleteCache.AddShortCache(Texture)` проверка наличия записи была инвертирована:
новая текстура не попадала в кратковременный кэш, а существующая запись заменялась
с лишним увеличением числа ссылок. Теперь запись создаётся только при её отсутствии.
Проверяются истечение через два прохода, повторное добавление, явное удаление
и сохранение поиска по descriptor.

При ограничении LRU-кэша сохраняется последняя, только что добавленная текстура,
даже если она одна превышает бюджет. Иначе `Add` мог снять последнюю ссылку и
освободить host texture до регистрации/возврата из `TextureCache.FindOrCreateTexture`.
Это мягкий бюджет: один слишком большой ресурс может его превысить.

### 7. Освобождение Vulkan-памяти после ошибки MapMemory

В `MemoryAllocatorBlockList.Allocate` успешный `AllocateMemory` предшествует
`MapMemory` и регистрации блока. При ошибке отображения блок ещё не принадлежит
списку и раньше терялся. Теперь allocation освобождается перед повторной передачей
исключения. Успешный путь регистрации и последующего освобождения сохранён.
Это исправление проверяется обзором владения и компиляцией; ошибка реального
драйвера в этой среде не воспроизводилась.

## Оставшиеся риски и условные блокеры порта

1. **P1, вытеснение GPU-буферов.** `BufferCache.EnforceCapacity` удаляет чистые буферы,
   но cached ranges и сохранённые привязки могут продолжить ссылаться на них.
   Fast paths `TranslateAndCreateMultiBuffers*` пропускают создание, затем `GetBuffer`
   может получить отсутствующий объект. `NotifyBuffersModified` запрашивает rebind,
   но не восстанавливает ресурс. Одной очистки `VirtualRangeCache` недостаточно:
   создание destination также может вытеснить source текущей операции. Нужны
   согласованные pinning/recreation и тесты bind/copy/multi-range при малом бюджете.
   В этой ветке этот более широкий дефект не исправлен; сборка остаётся экспериментальной.
2. **P2, повреждённый shader cache.** `DiskCacheHostStorage.ReadHostCode` выделяет
   массив по `UncompressedSize` из файла, а `ShaderBinarySerializer.Unpack` недостаточно
   проверяет длины/полноту данных. Ошибки могут выйти за штатные catch загрузчика;
   завершение его очередей не защищено общим `finally`. Нужны тесты испорченных файлов,
   проверки формата и ограничение ресурсов без произвольного отсечения корректных shaders.
3. **NRO и постоянный shader cache.** `ProcessLoader` отключает дисковый shader cache
   и сбрасывает TitleId для NRO даже при наличии NACP. Включение требует устойчивой
   идентификации homebrew с отсутствующими/повторяющимися ID. Периодический Vulkan
   pipeline cache является другим уровнем и не отменяет этого ограничения.
4. **Внешние данные.** Импорт в библиотеку копирует исполняемый файл в `Documents/roms`,
   SD размещается в `Documents/sdcard`. Порту с чтением `sdmc:/…` нужны соответствующие
   внешние файлы. Какая раскладка нужна версии из Rutracker, не установлено.
5. **Аргументы homebrew.** MeloNX запускает NRO без `argv`; Eden имеет такой путь.
   Влияние зависит от того, использует ли конкретный порт аргументы для путей/настроек.
6. **Диагностика GPU-памяти.** Apple cache budgets вычисляются из размера гостевой RAM,
   а не `os_proc_available_memory`. Memory warning сейчас только записывается.
   Счётчиков native allocations/текстур/буферов/очередей компиляции нет; для их
   безопасного добавления нужны снимки на потоках-владельцах ресурсов.

## Подготовка зависимостей

В новом клоне успешно выполнен `scripts/prepare-build.ps1`. Получены:

- .NET SDK 10.0.400 Windows x64, установлен в `.tools/dotnet`;
- архив того же SDK для macOS ARM64;
- Swift `melo-controller` на `efe0373ede6ca4dc7d6533d7fa47ad52b4230fe8`;
- Swift `navigation-stack-backport` на `55acfe7693c233ddc7f62f887f0df6ebd779ef01`;
- NuGet-пакеты решения и `ios-arm64`, включая `Ryujinx.LibHac 0.21.0-alpha.129`;
- Apple NativeAOT runtime и ILCompiler 10.0.11.

SHA512 обоих SDK проверен по официальным метаданным Microsoft. Основной хост
`builds.dotnet.microsoft.com` в этой среде не разрешился через DNS; архивы получены
с официального `dotnetcli.blob.core.windows.net` и прошли ту же проверку.
Обычный HTTP-запрос к upstream NuGet feed показывал Anubis, однако штатный
`dotnet restore` успешно получил пакет: действующего блокера LibHac в этой копии нет.

517 файлов встроенных iOS-зависимостей уже входят в Git. `.tools/` и `artifacts/`
исключены из Git; клон в другой папке сам по себе не переносит этот кэш.
Xcode/iOS SDK на Windows не устанавливаются этим скриптом; финальный нативный build
использует macOS и существующий workflow. Swift checkouts в Windows автоматически
не подставляются SwiftPM на Mac.

Остающиеся особенности воспроизводимости: NuGet transitives не закреплены lock-файлом;
Actions используют major-теги, `macos-26` — обновляемый образ. Packaging отдельно
проверяет точную версию .NET и Swift lock. При повторном локальном запуске старые файлы
`artifacts/ios` могут сохраняться после неудачной сборки: проверять exit code и `build-info.txt`.

## Как проверить GTA V дальше

Нужны точные версия iOS, название/версия Switch-порта и внешних данных, формат игры,
firmware, участок воспроизведения и экспорт диагностики с телефона. Номер темы или
ролик с другим устройством эти данные не заменяют.

Сравнивать исходный и новый commit с одинаковыми настройками JIT, разрешением и одним
участком игры. Начинать с Automatic JIT и выключенного Expand RAM; увеличение JIT-кэша проверять отдельно при
сообщении именно об его исчерпании. Для Vulkan сравнить количество checkpoint-сообщений,
память и повторный запуск после нормального выхода/аварии. Для различения JetSam,
ошибки гостевого процесса, файлов и GPU нужны соответствующие логи, а не только факт вылета.
Существующая [инструкция эксперимента](GTAV-EXPERIMENT.ru.md) остаётся основной.
