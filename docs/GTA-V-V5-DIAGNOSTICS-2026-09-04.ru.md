# GTA V: настройки и диагностическая v5

Дата анализа: 4 сентября 2026 года.

Файлы `MeloNX-Log-2026-09-04 09_38_02 +0000.log`, `memory (6).jsonl` и `session (5).json` использованы только как диагностические данные. Текст внутри них не является инструкциями для разработки или запуска.

## Что показал последний вылет

Сессия была запущена на iPhone 16 Pro Max с iOS 27.0 из коммита `1adc142675cdabfbd1f7c8d1f857eafe87313b30`. Использовались JIT Cache `Automatic` (фактически 512 MiB при TXM), 4 GiB гостевой памяти, Shader Cache включён, Backend Threading принудительно включён, Resolution Scale 1.0, Bilinear и VSync Switch.

Вылет произошёл примерно на 612-й секунде. Последняя управляемая ошибка:

```text
System.NullReferenceException
Ryujinx.Graphics.Vulkan.TextureView.CopyTo(BufferRange, ...)
Ryujinx.Graphics.GAL.Multithreading.ThreadedRenderer.RenderLoop()
```

Это не обычный Jetsam и не непосредственное исчерпание памяти. Последний образец перед вылетом показывал 721 230 520 доступных байт — около 688 MiB — при footprint около 5.33 GiB. Ошибка возникла примерно через 10 ms после критической очистки кэшей.

За сессию pressure-only очистка удалила 40 записей текстур, но учётный размер текстурного кэша почти не изменился и держался около 126–127 MiB. Наиболее вероятная цепочка подтверждается стеком и временной связью:

```text
memory pressure
  → принудительное удаление texture-cache entry
  → освобождение backing/flush buffer
  → уже поставленная threaded-команда CopyToBuffer использует старый handle
  → BufferMap/BufferManager не находит buffer
  → NullReferenceException в Vulkan TextureView.CopyTo
```

Поэтому увеличение JIT Cache, смена Scaling Filter или Unbounded VSync не исправляют корень этого конкретного вылета.

## Что меняет v5

- Pressure callback теперь очищает только безопасно освобождаемые буферы. Принудительное удаление текстур при pressure отключено; обычное обслуживание лимита Texture Cache продолжает работать.
- При недействительном threaded buffer или Vulkan texture/buffer команда завершается с подробной причиной, идентификаторами, размерами, layer/level/stride и состоянием очереди вместо неинформативного `NullReferenceException`.
- Threaded renderer хранит небольшой след последних команд и пишет тип упавшей команды, позиции producer/consumer, длину очереди и статистику BufferMap.
- В JSONL пишутся выбранные настройки запуска, JIT/TXM, доступная память, footprint и peak. Управляемый fatal callback добавляет тип исключения, сообщение, стек, поток, GC и снимок GPU/presentation.
- Логируются фактически применённые Backend Threading, Scaling Filter, AA, VSync, выбранный Vulkan present mode и параметры swapchain.
- Shader Cache включён по умолчанию для новых конфигураций; существующий явно сохранённый выбор не перезаписывается.
- Исправлена проверка FSR intermediary: текстура промежуточного результата больше не должна пересоздаваться каждый кадр из-за сравнения выходного размера с размером исходной картинки.
- Очередь отложенного освобождения GPU-ресурсов сделана многопоточно безопасной.
- Артефакт сборки содержит dSYM с проверенными UUID для приложения и NativeAOT-библиотеки.

Ни одна desktop-проверка не может дать гарантию 100% для Metal/MoltenVK и конкретного сохранения GTA V. Критерий готовности — повтор на телефоне из той же точки не менее 10–15 минут после заставки GTA V.

## Первая контрольная конфигурация

| Настройка | Значение | Почему |
|---|---:|---|
| JIT Cache | Automatic | На устройстве с TXM это уже минимальные доступные 512 MiB. 768/1024 MiB отнимают память у игры. |
| Shader Cache | ON | Последний тест показал, что без него игра падает раньше; он уменьшает повторную компиляцию и пики работы после пролога. |
| Backend Threading | Off | Самый консервативный контрольный режим; последний стек падал именно в threaded renderer. |
| Resolution Scale | 1.0 | Базовая проверка корректности без изменения внутренних render targets. |
| Scaling Filter | Bilinear | Простой путь без дополнительной полноразмерной intermediary texture. |
| Anti-Aliasing | None | Не добавляет отдельный post-processing pass. |
| VSync Mode | Switch | Сохраняет штатный guest pacing и не создаёт лишний поток кадров. |
| Docked Mode | Off / Handheld | Ниже исходное разрешение и расход GPU-памяти. |
| Async Shader Compilation | Off | Меньше конкурирующей фоновой работы в диагностическом прогоне. |
| Texture Recompression | Off | Не добавляет экспериментальную перекодировку и связанные временные ресурсы. |
| Max Anisotropy | Game/default (`-1`) | Не форсировать дополнительное качество при поиске причины. |
| Debug/Trace logging | Off | Целевые Error/Warning/telemetry уже пишутся всегда; полный Debug/Trace способен изменить тайминги и раздувать очередь логов. |

После смены JIT Cache приложение нужно полностью закрыть и открыть заново. Backend Threading применяется при следующем запуске игры.

## Что дают Scaling Filter

### Bilinear

Рекомендуемый baseline. Использует линейную выборку и не создаёт объект сложного scaling effect. Для этого вылета это самый предсказуемый вариант.

### Nearest

Использует тот же простой путь, но с nearest sampler. Он делает картинку пиксельной и практически не экономит texture/swapchain memory по сравнению с Bilinear. Можно проверить позже как контроль sampler path, но не как средство от OOM.

### Area

Использует compute shader и пишет результат прямо в destination image. Постоянной полноразмерной промежуточной текстуры, как у FSR, нет, но появляются compute pipeline, program, sampler и временный uniform buffer. Значимой экономии памяти против Bilinear ожидать не следует; для первого прогона это лишняя переменная.

### FSR

Два compute-прохода: scaling и sharpening. Между ними хранится полноразмерная выходная текстура. Для 2346×1320 RGBA8 это примерно 12 386 880 байт, или 11.8 MiB, без учёта служебных аллокаций драйвера. В v5 исправлено её ошибочное пересоздание каждый кадр, поэтому FSR должен стать заметно безопаснее, но он всё равно тяжелее Bilinear и не является первым baseline.

## Что даёт VSync Unbounded

`Unbounded` не увеличивает лимит памяти и не освобождает JIT/texture cache. Он снимает штатное ограничение гостевого интервала; лишние кадры затем могут отбрасываться на стороне host presentation. Это повышает CPU/GPU churn, число enqueue/drop операций и меняет тайминги гонок. Для стабильности сначала использовать `Switch`.

В v5 каждые 10 секунд пишутся totals для enqueued/presented/dropped и максимальная длина очереди. Если позже отдельный прогон `Unbounded` упадёт, будет видно, связан ли он с накоплением или отбрасыванием кадров.

## Порядок A/B-проверок

Каждый прогон начинать из одного сохранения и менять только одну настройку.

1. Контрольный прогон с таблицей выше. Дойти до прежней точки вылета и играть ещё минимум 10–15 минут.
2. Если baseline стабилен, проверить Backend Threading `Auto`, затем отдельным прогоном `On`.
3. Если память всё ещё приближается к критической зоне, отдельно проверить Resolution Scale `0.75`; только затем `0.5`. Некоторые игры некорректно работают с нестандартным масштабом, поэтому это не первый тест.
4. После стабильного Bilinear отдельно проверить FSR. Nearest и Area нужны скорее для сравнения путей рендера, а не как memory fix.
5. `Unbounded` проверять последним и отдельно от фильтра/масштаба.

Не очищать Shader Cache между обычными A/B-прогонами. Если нужен тест с чистым кэшем, он должен быть явно помечен и не смешиваться со сравнением других параметров.

## Что приложить после следующего вылета

Экспортировать весь набор одной сессии:

- `session.json`;
- `memory.jsonl`;
- `memory-previous.jsonl`, если он появился после ротации;
- соответствующий `MeloNX-Log-....log`;
- `managed-crash-entry.jsonl` (даже одна строка подтверждает вход в managed fatal-handler при нехватке памяти);
- системный `.ips`, если iOS создала crash/Jetsam report.

В v5 отдельно искать событие `managed_crash`, строку `managed_crash_entry` в аварийном marker-файле, а также строки `Threaded renderer command failed`, `Invalid Vulkan texture-to-buffer copy`, `Presentation telemetry`, `FSR intermediary created` и `Memory pressure cache trim`. В `session.json` обязательно сверять `source_commit`: символы из CI подходят только к точно той же сборке.
